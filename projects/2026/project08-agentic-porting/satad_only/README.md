# `satad_only` — saturation adjustment (Fortran + GT4Py) and its test harness

This folder holds the ICON saturation-adjustment kernel in isolation:

- `fortran/` — the original Fortran (`mo_satad.f90`) plus a single-column driver
  (`column_driver.f90`) that reads/writes CSV.
- `satad_gt4py.py` — the GT4Py (`gt4py.next`) port; `column_driver.py` is its CLI.
- `example/` — the shared sample column: `fields.csv` (input) and
  `output_fields.csv` (Fortran output, regenerated by the driver).
- `tests/` — the **native consistency harness** described below.
- `agents_plan_port/`, `agents_plan_test/`, `PORT_NOTES.md` — design plans and notes.

This folder *is* the `satad_only` Python package, so `FORTRAN_DIR` and
`EXAMPLE_DIR` (defined in `__init__.py`, anchored to the file rather than to the
working directory) are how the tests and the driver find their data.

## What the tests check

The harness proves the GT4Py port and the Fortran agree by running **both of
them natively** on identical inputs and comparing the adjusted `(tk, qv, qc)`:

- The **Fortran** side is the *actual compiled binary* (`mo_satad.f90` via
  `column_driver`), driven through temporary CSVs — see
  [tests/fortran_runner.py](tests/fortran_runner.py).
- The **GT4Py** side is the *actual DSL* running on its embedded backend, via
  `satad_numpy` in [satad_gt4py.py](satad_gt4py.py).

There is **no numpy re-implementation of the physics** anywhere in the trust
path — the reference is the real Fortran, not a hand transcription of it.

Comparison tolerance is `numpy.isclose(rtol=10e-12, atol=0)`; a tiny `atol`
(`1e-18`) is applied to `qc` only, because `qc` floors at `0.0` / `ZQWMIN=1e-20`
and can land near zero where a purely relative bound is unusable. The scenarios
([tests/scenarios.py](tests/scenarios.py)) cover the bundled column plus
generated edge cases: dry/unchanged, evaporation (branch A), supersaturation
(branch B), a near-zero-`qc` column, and a random multi-level column.

> Note: on a machine where gfortran and numpy share the same libm, the two
> implementations currently agree **bit-for-bit**, so the tolerance passes with
> large margin. `rtol=10e-12` (and the `qc` `atol`) are the safety margin for
> platforms whose libm `exp` differs at the ULP level.

## Environment setup

Two toolchains are needed.

**1. Python (GT4Py side)** — managed with [uv](https://docs.astral.sh/uv/) in a
single repo-root virtual environment (`.venv/`). From the **repository root**:

```bash
uv sync
```

This installs numpy, the vendored editable `gt4py`, and pytest (pulled in via
gt4py's testing extras) from the committed `uv.lock`, and downloads a compatible
Python (≥3.10) if needed. No manual activation is required — prefix commands with
`uv run`.

**2. Fortran (reference side)** — a Fortran compiler, `gfortran` by default
(e.g. `brew install gcc` on macOS, `apt install gfortran` on Linux). The test
harness builds the driver automatically (`make driver`) the first time it runs;
you do not need to build it by hand. If your compiler is named differently, set
`FC`:

```bash
export FC=gfortran-16   # picked up by both make and the harness
```

## Running the tests

From the **repository root**:

```bash
uv run pytest satad_only/tests/ -v
```

That's it — a pytest session fixture builds `fortran/build/column_driver` before
the first test, and each test shells out to that binary via throwaway temp CSVs
(the committed `example/output_fields.csv` is never modified by a test run). The
suite is CWD-independent (every path is anchored to `__file__`), so it runs the
same from anywhere — inside `satad_only/`, or outside the repo entirely.

If you have activated the venv (`source .venv/bin/activate`) or are not using
uv, the equivalent is:

```bash
python -m pytest satad_only/tests/ -v
```

## Running either driver on its own (optional)

Both implementations ship a single-column driver with the **same CLI and CSV
contract** (`rho,tk,qv,qc`), so you can run each in isolation on the `example/`
column and diff the results. Both write at full float64 precision (~17
significant figures).

**Fortran** — `column_driver [in_csv [out_csv [tol [maxiter]]]]`; omitted
arguments default to `../example/fields.csv`, `../example/output_fields.csv`,
`tol=1e-3`, `maxiter=10`. From `satad_only/fortran/`:

```bash
make run                                        # defaults: reads ../example/fields.csv
./build/column_driver in.csv out.csv 1.0e-3 10  # explicit
```

**GT4Py** — [column_driver.py](column_driver.py), same signature, defaulting to
this folder's `example/fields.csv` and `example/output_fields_gt4py.csv`. From
anywhere:

```bash
uv run python -m satad_only.column_driver                  # defaults
uv run python -m satad_only.column_driver in.csv out.csv 1.0e-3 10
```

(`maxiter` is fixed at 10 in the GT4Py port — the Newton loop is unrolled that
many times — so a different value is rejected rather than silently ignored.)

The two outputs are directly comparable, e.g.:

```bash
uv run python -c "import numpy as np; \
  f=np.loadtxt('satad_only/example/output_fields.csv',delimiter=',',skiprows=1); \
  g=np.loadtxt('satad_only/example/output_fields_gt4py.csv',delimiter=',',skiprows=1); \
  print('max abs diff:', np.max(np.abs(f-g)))"
```
